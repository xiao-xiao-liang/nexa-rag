# AI 中台前端设计

**日期：** 2026-07-25
**状态：** 已确认
**技术栈：** React、Vite、TypeScript

## 1. 背景与目标

当前后端已具备 RAG 文档管理、会话和流式对话能力。本次新增独立前端工程，将产品定位为可扩展的 AI 中台，而不是单一 RAG 应用。

第一期只接入现有 RAG 接口，完成可用的对话工作台。数据分析 Agent、智能差旅 Agent 暂无后端接口，不提供伪造的业务功能，但在前端架构和交互中保留扩展位置。

目标如下：

1. 提供以对话为核心的统一工作台。
2. 支持 RAG SSE 流式输出、取消、失败恢复和引用展示。
3. 使新增 Agent 只需要补充前端定义和事件渲染器，不需要重构会话与消息主体。
4. 不修改现有后端接口、模块或数据库。

## 2. 范围与非目标

### 2.1 第一期开范围

1. 新建 React + Vite + TypeScript 前端工程。
2. 实现统一会话列表、RAG 对话、流式消息、引用和状态消息。
3. 基于 Apifox 现有接口封装文档与对话请求。
4. 为扩展 Agent 预留前端元数据和可插拔事件渲染机制。
5. 覆盖核心事件转换与交互的自动化测试。

### 2.2 第一期开不包含

1. 数据分析 Agent、智能差旅 Agent 的真实接口调用和业务页面。
2. 后端新增 `agentId` 请求参数、路由、意图识别或跨 Agent 编排。
3. 跨 Agent 共享上下文、跨 Agent 会话切换和协同执行。
4. 固定右侧信息栏或独立的多 Agent 工作台页面。

## 3. 页面与交互设计

采用双栏聚焦对话布局。

### 3.1 左侧：统一会话列表

左侧仅按时间和主题展示全部会话，并提供新建会话入口。会话不按 Agent 分栏，也不将 Agent 作为一级导航。

每个会话在前端保存其创建时的 `agentId` 元数据。第一期所有会话均为 `rag`，该字段不传给后端；它只用于未来恢复会话时选择对应的渲染器和交互能力。

### 3.2 主区域：消息时间线

主区域展示欢迎态、用户消息、助手流式消息、状态消息与错误消息。输入区固定在底部，历史消息向上滚动。

RAG 返回的检索引用和处理状态以内联可折叠消息块显示，不增加固定右栏。这样第一期保持阅读聚焦，同时允许后续 Agent 把图表、行程、工具结果等以新的内联消息块接入。

### 3.3 底部：功能选择器

RAG 是默认能力，不作为可选标签显示。用户未选其他功能时，发送消息直接按现有 RAG 接口处理。

输入框底部预留功能选择区，后续数据分析、智能差旅等 Agent 以可选择、可取消的标签出现。选择某个扩展能力并发送首条消息时，前端创建一个绑定该 `agentId` 的独立会话。第一期扩展能力没有可用接口，因此仅保留组件、类型和禁用或说明态，不发送伪造请求。

已创建会话固定使用创建时的 Agent；不允许在原会话中切换 Agent，避免后续意图识别和上下文边界混乱。

## 4. 前端架构

### 4.1 组件边界

1. `ConversationSidebar`：加载、创建、选择和分组展示会话。
2. `ChatWorkspace`：组合消息区和输入区，管理当前会话生命周期。
3. `MessageTimeline`：按顺序渲染消息并处理滚动跟随。
4. `MessageRenderer`：依据标准化事件与消息类型选择文本、错误、状态、引用等渲染块。
5. `Composer`：维护输入内容、发送、停止生成和功能选择。
6. `AgentSelector`：展示可用扩展功能；第一期不展示 RAG 标签。
7. `CitationBlock` 与 `StatusBlock`：以可折叠内联块展示 RAG 附加信息。

### 4.2 状态分层

1. 服务端状态：会话、历史消息、文档引用等由接口请求获取。
2. 流式状态：当前请求标识、累积文本、连接状态、取消状态和事件缓冲独立维护。
3. 界面状态：输入内容、引用展开状态、功能选择、滚动跟随等仅在界面层维护。

三类状态分离，避免单个 SSE 增量更新触发页面无关区域刷新。

### 4.3 Agent 与事件扩展

前端定义 `AgentDefinition`，包含 `id`、名称、可用状态、输入提示和事件渲染器注册信息。第一期内置默认 `rag` 定义，其余 Agent 仅作为预留定义。

后端 SSE 原始事件先被转换为统一的 `ChatEvent`：文本增量、引用、状态、完成、取消和错误。`MessageRenderer` 通过注册表处理事件；未知 Agent 或未知事件显示安全的通用信息块并记录前端诊断，不影响已收到的正常内容。

当前后端不支持 `agentId`，因此请求层不得将该字段加入 URL、请求头或请求体。它只保存在前端会话元数据中。

## 5. 流程与异常处理

1. 用户选择或新建会话；未选择扩展功能时默认使用 RAG。
2. 用户输入并提交后，前端立即写入用户消息和进行中的助手消息。
3. 前端连接现有 RAG SSE 接口，将每个事件标准化后增量更新助手消息及其内联块。
4. 收到完成事件后，将进行中的消息转为已完成消息。
5. 用户主动停止时调用现有取消接口，保留已收到内容并标记“已停止”。
6. 网络中断、接口业务错误或解析失败时，保留已收到文本，在消息尾部展示可重试或重新生成操作。
7. 空输入、无当前会话和不可用扩展能力必须显示明确提示，不得以完成态掩盖错误。

## 6. 接口使用原则

接口以 Apifox 文档为唯一契约来源。第一期使用现有文档、会话和 RAG 流式对话接口，不新增或变更后端契约。

接口封装层统一处理基础地址、响应信封、错误码、SSE 解码与取消请求。页面组件不得直接拼接请求 URL 或解析原始事件字符串。

## 7. 验证策略

1. 单元测试：SSE 文本增量拼接、引用映射、状态映射、取消映射、错误映射和未知事件降级。
2. 组件测试：默认 RAG 发送、会话选择、流式内容展示、引用折叠、停止生成和错误重试入口。
3. 构建验证：TypeScript 类型检查与 Vite 生产构建。
4. 手工验证：使用现有后端和 Apifox 契约完成一次真实 RAG 流式对话、取消和异常提示检查。

## 8. 验收标准

1. 用户无需选择功能即可发起 RAG 对话并看到流式回答。
2. 左侧会话列表统一展示，不以 Agent 分栏。
3. RAG 引用和状态以内联块呈现，页面没有固定右栏。
4. 停止、错误和网络中断都能保留已接收内容并给出明确状态。
5. `agentId` 仅存在于前端会话元数据，网络请求不包含该字段。
6. 新增 Agent 时不需要修改会话列表和主消息时间线的核心结构。
