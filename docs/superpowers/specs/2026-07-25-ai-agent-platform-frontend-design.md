# AI 中台前端设计

**日期：** 2026-07-25
**状态：** 已确认
**技术栈：** React、Vite、TypeScript、Tailwind CSS、shadcn/ui、Lucide

## 1. 背景与目标

当前后端已具备 RAG 文档管理、会话和流式对话能力。本次新增独立前端工程，将产品定位为可扩展的 AI 中台，而不是单一 RAG 应用。

第一期只接入现有 RAG 接口，完成可用的对话工作台。数据分析 Agent、智能差旅 Agent 暂无后端接口，不提供伪造的业务功能，但在前端架构和交互中保留扩展位置。

目标如下：

1. 提供以对话为核心的统一工作台。
2. 支持 RAG SSE 流式输出、取消与失败恢复，并为检索引用展示预留扩展位置。
3. 使新增 Agent 只需要补充前端定义和事件渲染器，不需要重构会话与消息主体。
4. 补充会话列表与历史消息查询接口，作为前端恢复会话的服务端事实来源。

## 2. 范围与非目标

### 2.1 第一期开范围

1. 新建 React + Vite + TypeScript 前端工程。
2. 实现统一会话列表、RAG 对话、流式消息和状态消息。
3. 基于 Apifox 现有接口封装文档、会话查询与对话请求。
4. 为扩展 Agent 预留前端元数据和可插拔事件渲染机制。
5. 覆盖核心事件转换与交互的自动化测试。
6. 新增当前用户的会话列表和会话历史消息查询接口。

### 2.2 第一期开不包含

1. 数据分析 Agent、智能差旅 Agent 的真实接口调用和业务页面。
2. 后端新增 `agentId` 请求参数、意图识别或跨 Agent 编排。
3. 跨 Agent 共享上下文、跨 Agent 会话切换和协同执行。
4. 固定右侧信息栏或独立的多 Agent 工作台页面。

## 3. 页面与交互设计

采用双栏聚焦对话布局。

### 3.1 左侧：统一会话列表

左侧仅按时间和主题展示全部会话，并提供新建会话入口。会话不按 Agent 分栏，也不将 Agent 作为一级导航。

每个会话在前端保存其创建时的 `agentId` 元数据。第一期所有会话均为 `rag`，该字段不传给后端；它只用于未来恢复会话时选择对应的渲染器和交互能力。会话列表以服务端持久化记录为唯一事实来源，按最近更新时间倒序分页加载。

### 3.2 主区域：消息时间线

主区域展示欢迎态、用户消息、助手流式消息、状态消息与错误消息。输入区固定在底部，历史消息向上滚动。

RAG 处理状态以内联消息块显示，不增加固定右栏。检索引用组件仅保留扩展位置，待后端补齐引用 SSE 事件与历史引用数据契约后再展示。这样第一期保持阅读聚焦，同时允许后续 Agent 把引用、图表、行程、工具结果等以新的内联消息块接入。

### 3.3 底部：功能选择器

RAG 是默认能力，不作为可选标签显示。用户未选其他功能时，发送消息直接按现有 RAG 接口处理。

输入框底部预留功能选择区，后续数据分析、智能差旅等 Agent 以可选择、可取消的标签出现。选择某个扩展能力并发送首条消息时，前端创建一个绑定该 `agentId` 的独立会话。第一期扩展能力没有可用接口，因此仅保留组件、类型和禁用或说明态，不发送伪造请求。

已创建会话固定使用创建时的 Agent；不允许在原会话中切换 Agent，避免后续意图识别和上下文边界混乱。

## 4. 前端架构

### 4.1 视觉与组件系统

首期采用“安静专业”的默认亮色界面，延续参考图的白色表面、蓝色焦点边框和圆角输入区。使用 Tailwind CSS 管理语义化颜色、间距、圆角和阴影令牌；使用 shadcn/ui 作为可本地维护的基础组件；全部结构性图标使用 Lucide，禁止使用 Emoji 图标。

工作台优先使用 `Button`、`Textarea`、`ScrollArea`、`Tooltip`、`DropdownMenu`、`Collapsible`、`Skeleton`、`Sheet` 与 `Dialog`。消息时间线、会话行和状态块维持业务自有组件，避免把对话领域逻辑耦合到组件库。首期只实现亮色主题；暗色主题保留为设计令牌扩展，不在本期交付。

交互元素必须提供键盘焦点、可访问名称和禁用状态；图标按钮使用 44×44 像素的可点击区域。流式状态在 300 毫秒以上的等待场景显示骨架或状态反馈，动画只使用 150–300 毫秒的透明度或位移过渡。

### 4.2 组件边界

1. `ConversationSidebar`：加载、创建、选择和分组展示会话。
2. `ChatWorkspace`：组合消息区和输入区，管理当前会话生命周期。
3. `MessageTimeline`：按顺序渲染消息并处理滚动跟随。
4. `MessageRenderer`：依据标准化事件与消息类型选择文本、错误、状态、引用等渲染块。
5. `Composer`：维护输入内容、发送、停止生成和功能选择。
6. `AgentSelector`：展示可用扩展功能；第一期不展示 RAG 标签。
7. `StatusBlock`：以内联块展示 RAG 处理状态；`CitationBlock` 仅保留组件扩展位置。

### 4.3 状态分层

1. 服务端状态：会话列表、历史消息、文档引用等由接口请求获取。
2. 流式状态：当前请求标识、累积文本、连接状态、取消状态和事件缓冲独立维护。
3. 界面状态：输入内容、引用展开状态、功能选择、滚动跟随等仅在界面层维护。

三类状态分离，避免单个 SSE 增量更新触发页面无关区域刷新。

### 4.4 Agent 与事件扩展

前端定义 `AgentDefinition`，包含 `id`、名称、可用状态、输入提示和事件渲染器注册信息。第一期内置默认 `rag` 定义，其余 Agent 仅作为预留定义。

后端 SSE 原始事件先被转换为统一的 `ChatEvent`：文本增量、状态、完成、取消和错误；引用事件类型仅作为后续扩展保留。`MessageRenderer` 通过注册表处理事件；未知 Agent 或未知事件显示安全的通用信息块并记录前端诊断，不影响已收到的正常内容。

当前后端不支持 `agentId`，因此请求层不得将该字段加入 URL、请求头或请求体。它只保存在前端会话元数据中。

## 5. 流程与异常处理

1. 用户选择或新建会话；未选择扩展功能时默认使用 RAG。
2. 用户输入并提交后，前端立即写入用户消息和进行中的助手消息。
3. 前端连接现有 RAG SSE 接口，将每个事件标准化后增量更新助手消息及其状态内联块。
4. 收到完成事件后，将进行中的消息转为已完成消息。
5. 用户主动停止时调用现有取消接口，保留已收到内容并标记“已停止”。
6. 网络中断、接口业务错误或解析失败时，保留已收到文本，在消息尾部展示可重试或重新生成操作。
7. 空输入、无当前会话和不可用扩展能力必须显示明确提示，不得以完成态掩盖错误。

## 6. 会话查询接口契约

会话读取 REST 层归属 `nexa-rag-chat`：`ConversationController`、会话/消息安全响应 VO、`ConversationHistoryPageVO` 都位于 `com.nexarag.chat.controller` 及其 `vo` 子包。现有 `ChatController` 与 `ChatStreamRequest` 继续保留在 `nexa-rag-boot`，因为其直接协调 workflow 流式执行。

会话创建仍由现有流式聊天接口在首条消息时完成，前端从 `META` SSE 事件取得服务端生成的 `conversationId`。本次只增加读取接口，不新增前端本地会话作为事实来源的写入接口。

### 6.1 查询会话列表

`GET /api/conversations?current={current}&size={size}`

1. 用户身份必须从现有鉴权上下文读取，不接收用户 ID 查询参数。
2. 返回当前用户未删除的会话轻量投影，按 `updatedTime` 倒序，支持页码分页。
3. 仅返回前端列表所需的会话 ID、标题、状态、最近消息时间、创建时间和更新时间，不暴露用户 ID、乐观锁版本等内部字段。

### 6.2 查询会话历史消息

`GET /api/conversations/{conversationId}/messages?beforeSequence={beforeSequence}&size={size}`

1. 用户身份从鉴权上下文读取，服务端必须同时校验 `conversationId + userId` 归属。
2. `beforeSequence` 为空时读取最新一页；传入时读取序号小于该值的一页。服务端按 `sequence` 倒序查询，再按升序返回给前端。
3. 响应包含记录、是否还有更早记录和下一页 `beforeSequence`，前端据此上拉加载并保持消息显示顺序。
4. 历史消息必须返回 `COMPLETED`、`FAILED`、`CANCELLED` 三种终态及其已生成内容；`GENERATING` 仅在服务端真实存在时按状态返回，不伪装为完成。
5. 外部消息投影不暴露用户 ID、思考内容、原始引用 JSON 与内部失败明细；历史接口不对外提供引用数据，直至引用数据契约补齐。

## 7. 领域术语与决策记录

### 7.1 术语表

| 术语 | 含义 | 非含义 |
| --- | --- | --- |
| 会话 | 当前用户拥有的持久化 RAG 对话容器，以 `conversationId` 标识 | 不是一次生成任务 |
| 消息 | 会话中按 `sequence` 严格排序的持久化用户或助手内容 | 不是 SSE 分片 |
| 生成任务 | 一次助手回答的运行期控制对象，以 `generationId` 取消 | 不是会话或历史查询主键 |
| 会话列表项 | 用于侧栏展示的会话轻量投影 | 不承载完整消息正文 |
| 历史消息 | 由服务端持久化的消息序列 | 不等同于模型上下文缓存 |

### 7.2 ADR-001：历史记录以持久化数据为唯一事实来源

**背景：** SSE 只承载当前生成过程，浏览器内存和本地缓存无法支持跨连接、跨设备的完整会话恢复。

**决策：** 会话列表读取持久化会话数据，历史消息读取持久化消息数据；前端缓存只用于界面加速，不能替代服务端查询。

**备选方案：** 仅在浏览器本地保存会话和消息，或根据 SSE 与运行期生成任务拼装历史。

**理由：** 现有领域服务已经具备用户归属、逻辑删除、消息顺序和生成终态，能够提供正确的权限边界和重连恢复。

**后果：** 后端需要维护读取接口和外部响应投影；前端需要处理列表页码分页与历史游标分页。

### 7.3 ADR-002：历史消息采用序号游标分页并保留所有终态

**背景：** 固定读取最近 N 条消息不能覆盖长会话的完整回看，也会掩盖用户主动停止或生成失败的真实结果。

**决策：** 历史接口以 `sequence` 作为向前游标，返回全部终态消息和已生成部分内容。

**备选方案：** 仅返回最近 N 条，或使用页码分页历史消息。

**理由：** 消息序号在会话内单调递增，适合高效读取更早消息，并能让前端稳定保持时间线顺序。

**后果：** 前端需要实现上拉加载和锚点保持；接口需提供 `hasMore` 与下一页游标。

### 7.4 ADR-003：通用分页对象归属 common 模块

**背景：** document 模块已有仅供自身使用的 `PageVO`，会话列表也需要相同分页元信息。

**决策：** 将 `PageVO<T>` 提取到 `nexa-rag-common` 并改为普通泛型类；文档与会话分页响应复用该类并通过子类补充各自的领域命名。游标分页使用独立普通类，不从页码分页对象继承。

**备选方案：** 在 chat 模块重复定义分页对象，或保留 document 模块类型并由 chat 依赖 document。

**理由：** 页码分页元信息属于跨领域基础能力；chat 依赖 document 会破坏模块方向。普通类允许领域分页 VO 继承通用字段，且不受 Java record 的 final 限制。

**后果：** 需要迁移 document 的导入和测试，并为 common 的分页对象补充兼容性测试。

## 8. 接口使用原则

接口以 Apifox 文档为唯一契约来源。第一期使用现有文档、会话查询和 RAG 流式对话接口；新增会话查询接口完成后，必须同步补充到 Apifox。

接口封装层统一处理基础地址、响应信封、错误码、SSE 解码与取消请求。页面组件不得直接拼接请求 URL 或解析原始事件字符串。

## 9. 验证策略

1. 后端测试：会话列表按用户过滤与排序、历史游标边界、跨用户访问拒绝、终态消息可见性和响应投影脱敏。
2. 单元测试：SSE 文本增量拼接、状态映射、取消映射、错误映射和未知事件降级。
3. 组件测试：默认 RAG 发送、会话选择、上拉加载历史、流式内容展示、停止生成和错误重试入口。
4. 构建验证：TypeScript 类型检查与 Vite 生产构建，以及新增后端接口的针对性测试。
5. 手工验证：新建会话、流式回答、停止、刷新恢复、历史上拉、会话切换与跨用户访问拒绝。

## 10. 验收标准

1. 用户无需选择功能即可发起 RAG 对话并看到流式回答。
2. 左侧会话列表从服务端加载并统一展示，不以 Agent 分栏。
3. RAG 状态以内联块呈现，页面没有固定右栏；引用展示能力仅预留扩展位置。
4. 停止、错误和网络中断都能保留已接收内容并给出明确状态。
5. `agentId` 仅存在于前端会话元数据，网络请求不包含该字段。
6. 重新进入会话后，可通过服务端历史接口按序恢复所有终态消息与已生成内容。
7. 会话列表与历史查询只能返回当前用户拥有的数据，且外部响应不泄露内部字段。
8. 新增 Agent 时不需要修改会话列表和主消息时间线的核心结构。
