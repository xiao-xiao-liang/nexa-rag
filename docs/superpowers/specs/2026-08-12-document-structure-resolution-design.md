# 文档结构恢复与层级切分设计

## 1. 目标

在飞书导出的 DOCX 和 MinerU 解析的 PDF 中恢复可追溯的章节层级，构建独立于 Markdown 标题标记的文档树，并以该文档树驱动现有父子切分、章节导航和正文检索。

目标是提升标题语义与正文块的召回关联性；Markdown 继续作为已发布的展示制品和正文载体，但不再是唯一的结构事实。

## 2. 范围与阶段

本项工作拆为三个可独立交付的阶段。

### 阶段一：结构证据保留与保守修复

- PDF 的 MinerU 请求保留中间 JSON，并将其作为解析制品发布。
- DOCX 保留 Pandoc 生成的 Markdown，同时读取 Word 段落样式、编号及排版证据。
- 新增统一的候选标题、结构证据、章节节点和文档树模型。
- 基于可信 Markdown 标题、Word 标题样式和编号规则恢复章节树。
- Markdown 结构局部异常时保留可信子树，不再整篇退化为普通窗口切分。

本阶段不调用 LLM，不改变 MinerU 与 Pandoc 的格式路由，不批量重新处理历史文档。

### 阶段二：PDF 多信号层级恢复

- 从 PDF Outline/Bookmark、MinerU 标题块、编号、页码和版式证据恢复 PDF 标题层级。
- 证据优先级固定为：PDF 书签、标题编号、文档内相对样式、原始 MinerU 层级。
- 记录每个标题的层级来源、置信度和原始位置，供诊断与后续调参。

### 阶段三：低置信标题与检索评测

- 仅向 LLM 发送低置信的相邻标题上下文和脱敏后的结构特征，返回可校验的层级与置信度。
- 引入真实问答回归集，比较结构可用率、标题路径完整率和 Recall@K。
- 评测通过后再确定是否启用 LLM 兜底及其阈值。

## 3. 领域模型

| 对象 | 含义 | 所有者 | 非含义 |
| --- | --- | --- | --- |
| `DocumentStructureEvidence` | 解析器提供的结构信号，如 Markdown 标题、Word 样式、编号、PDF 页码和书签 | infra parser | 可索引正文 |
| `HeadingCandidate` | 尚未确定层级的标题候选，带原始顺序和证据 | structure resolver | 已持久化章节 |
| `DocumentSectionNode` | 已确定父子关系的章节节点 | document splitter | 超长正文的父块 |
| `DocumentContentBlock` | 归属章节的正文、表格、代码或图片块 | document splitter | 标题本身 |
| `DocumentStructureTree` | 一篇文档的章节和内容块顺序树 | structure resolver | Markdown 展示文件 |

`DocumentSectionDO` 继续是持久化章节事实；`DocumentChunk.parentChunkId` 仍只表示超长正文的窗口父子关系，不能用来表达章节父子关系。

## 4. 结构恢复规则

### 4.1 DOCX

1. Pandoc 输出的 `#` 至 `######` 标题是最高优先级的结构证据。
2. Word 段落的标准 `w:outlineLvl` 优先映射为对应层级；`Heading 1` 至 `Heading 6` 和明确配置的自定义标题样式作为补充证据。这样飞书导出时即使样式 ID 退化为数字，也能保留标准大纲语义。
3. 对无语义样式的飞书导出文档，仅在段落同时满足编号形态、整段强调和标题长度限制等规则时生成候选标题。
4. 启发式候选必须带置信度；低于阈值时保留为正文，不能伪造章节。
5. Word 标题与 Pandoc Markdown 行定位前需统一去除 Markdown 标题符号、强调标记和转义符；定位失败时记录诊断并保留正文，不按 DOCX 段落序号猜测 Markdown 行号。

### 4.2 PDF

1. PDF Outline/Bookmark 与 MinerU 标题块按文本相似度和页码匹配；成功匹配时书签层级为权威来源。
2. 未匹配书签的标题按编号规则推断层级，至少支持阿拉伯数字、多级编号、中文章节和括号编号。
3. 对无编号标题，仅在中间 JSON 存在可用版式信息时，以同文档的相对字号/行高分组推断层级；不使用跨文档固定字号阈值。
4. 无可靠证据的 MinerU 标题保留为同级候选或普通正文，不强行构造深层关系。

## 5. 切分与索引

1. 切分器以 `DocumentStructureTree` 为输入，优先在叶子章节内聚合正文块；超长块再按 Embedding tokenizer 的 token 上限切分。
2. 表格、代码块和图片及其相邻说明保持原子性；仅当单个原子块超过上限时才允许块内切分。
3. 每个可索引子块继承完整 `headingPath`，并继续使用“文档标题 + 标题路径 + 正文”作为 `indexContent`。
4. 章节导航索引只保存章节标题和路径；回答证据仍必须来自正文块。
5. 标题前的封面、摘要和导语挂到隐式根节点；单处标题跳级只影响该候选的置信度，不触发全文非结构化降级。

## 6. 制品、兼容性与安全

- `parsed/{documentId}/content.md` 保持现有主 Markdown 路径。
- PDF 额外发布受限的结构副产物，例如 `parsed/{documentId}/structure/mineru-middle.json`；它仅用于服务端结构恢复和运维诊断，不直接向匿名用户暴露。
- 新增的解析制品纳入现有 `parsed/{documentId}/` 前缀清理。
- LLM 兜底必须显式配置、可关闭，并且不发送完整文档、原始图片、凭据或不必要的正文。

## 7. 验收

阶段一至少覆盖：

1. 规范 Word 标题经 Pandoc 后保留多级章节树。
2. 飞书风格的加粗编号段落仅在启发式满足时被提升为标题。
3. Markdown 前言、局部跳级和混合标题不会导致整篇窗口降级。
4. MinerU ZIP 中间 JSON 可安全提取、发布和清理。
5. 所有可索引子块拥有正确的标题路径，父子窗口关系与章节关系不混淆。

阶段二使用包含 PDF Outline、编号标题和无编号样式标题的样本分别验证来源优先级和置信度。阶段三以脱敏的真实问答集比较改造前后的 Recall@K，未达到预定阈值不得默认启用 LLM 兜底。

## 8. 不采纳的方案

- 不整体替换 MinerU 为 Docling：MinerU 继续负责现有 PDF 的 OCR、表格、图片和复杂版面解析。
- 不把所有加粗段落直接提升为标题：这会把强调文本错误切成章节，破坏召回。
- 不让 LLM 全文重建目录：成本、隐私和稳定性不可控；仅处理规则无法判定的少量候选。
