# ADR：采用规范化 RBAC 角色、权限与关联表

## 状态

已被《在用户表保存一期唯一全局角色》替代。

## 背景

系统目前需要区分管理员与普通用户，并预期未来继续扩展角色和权限。仅在账号表保存单一角色枚举虽简单，但会把权限定义和关联演进推迟到破坏性迁移。

## 决策

1. 使用 `auth_role` 保存角色定义，`auth_permission` 保存权限定义。
2. 使用 `auth_account_role` 表达账号与角色的多对多关系，使用 `auth_role_permission` 表达角色与权限的多对多关系。
3. 一期初始化 `ADMIN`、`USER`；默认管理员持有 `ADMIN`，其余新账号持有 `USER`。
4. `/api/model/**` 对应的权限仅授予 `ADMIN`；精确权限码和表字段将在数据库迁移设计时连同现有接口逐项审查。
5. 一期不提供在线角色、权限或关联关系的编辑入口；表结构为后续治理预留，不表示开放自助授权。

## 备选方案

### 账号表单一角色枚举

拒绝。短期实现简单，但无法自然表达角色与权限的多对多关系，后期演进需要变更认证和授权核心表。

### 仅一张关联表

拒绝。账号—角色与角色—权限是不同关系，一张表无法无歧义地表达两者。

### 直接按账号赋予权限

拒绝。会绕过角色聚合，导致权限审计、批量治理与未来角色管理复杂化。

## 后果

- 认证上下文与 Sa-Token 授权适配层必须基于 `accountId` 读取角色和权限，不得依据账号名或前端参数判断。
- 数据库迁移需要为四张表配置唯一约束、关联索引、初始化数据与审计策略；具体字段将在实施前设计审查。
- 后续可增加角色、权限、租户范围或审批机制，但应维持账号—角色—权限的明确关系。
