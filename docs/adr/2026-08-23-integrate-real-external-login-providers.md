# ADR：一期真实接入 QQ、飞书、Google 与 GitHub 登录

## 状态

已接受。

## 背景

NexaRAG 一期需支持 QQ 扫码、飞书扫码、Google 和 GitHub 第三方登录，并支持将一个已认证第三方身份绑定到已有账号。该能力需要真实平台应用注册、授权回调和服务器端授权码交换，不能以模拟身份或客户端自报的第三方用户 ID 替代。

## 决策

1. 一期真实接入 QQ、飞书、Google 和 GitHub 四个平台的网页登录或扫码授权流程。
2. 每个平台仅请求确认外部主体所需的最小身份权限，不请求仓库、文档、通讯录等业务数据权限。
3. 所有授权码交换、外部主体标识校验和账号绑定均在服务端完成；外部主体唯一键只使用平台稳定且不可变的主体标识，不使用昵称、可变账号名或邮箱。
4. 仅为登录和绑定目的获取第三方身份信息后，不持久化第三方访问令牌或刷新令牌；成功后只保留最小化的第三方身份绑定记录。
5. 平台 Client ID、Client Secret、开发/生产回调基地址仅通过部署环境变量或密钥管理注入，禁止提交配置文件、测试夹具、日志或前端构建产物。
6. 授权回调统一使用服务端路径 `/api/auth/oauth/{provider}/callback`，其中 `{provider}` 为 `qq`、`feishu`、`google` 或 `github`；生产回调基址固定为 `https://xiaoxiaoliang.top`，即各平台生产回调 URL 为 `https://xiaoxiaoliang.top/api/auth/oauth/{provider}/callback`。开发回调基址在可公网访问的 HTTPS 开发域名确定后以环境配置提供，不得写死在代码中。
7. OAuth/扫码流程必须使用服务端短期、单次消费的 `state`，绑定账号、用途、回调提供方与 PKCE（平台支持时）；回调失败、state 失效或主体校验失败不得建立 Sa-Token 会话或改变绑定。
8. GitHub 登录使用一个 GitHub App，而非 OAuth App；该 App 后续同时登记开发与生产回调 URL。
9. 四种第三方登录成功并建立新的 Sa-Token 会话时，服务端同时为该新会话签发 15 分钟最近验证授权；该授权不得跨会话复用，也不能替代更换邮箱的旧、新邮箱独立验码或密码重置流程。

## 备选方案

### 使用模拟第三方身份或由前端传入第三方用户 ID

拒绝。无法证明第三方主体真实归属，且可被伪造为任意账号。

### 在浏览器直接交换授权码并保存第三方 Token

拒绝。会暴露 Client Secret 或用户 Token，扩大 XSS 与供应商 Token 泄露风险。

### 为登录长期保存第三方访问/刷新 Token

拒绝。登录身份绑定不需要代表用户调用第三方业务 API；长期保存 Token 只会扩大敏感数据与轮换负担。

## 后果

- 部署前必须由应用所有者在各平台创建开发、生产应用或等价环境配置，并安全提供 Client ID、Secret 和精确回调 URL。
- GitHub App 可登记多个回调 URL，因此在部署域名确定后向同一个 App 补充开发与生产地址；在地址确定前不得启用或测试 GitHub 登录回调。
- 后端需要为每个平台实现受测试覆盖的适配器、错误映射、回调状态机和配置校验；前端只负责跳转、展示扫码/授权状态与回调完成后的导航。
- 第三方登录成功创建的最近验证授权必须与 Sa-Token 会话建立原子完成；若会话建立失败，不得留下可用授权。
- 供应商应用凭据、回调地址、最小 scope 和审核/发布状态应记录在部署文档，不应记录 Secret 值。
