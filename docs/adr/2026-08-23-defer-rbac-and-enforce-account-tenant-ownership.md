# ADR：一期不引入 RBAC，按账号与租户归属实施授权

## 状态

已被《一期引入最小管理员授权边界》替代。

## 背景

NexaRAG 正在从固定本地用户过渡到真实账号登录。项目已有按租户隔离知识库和文档的方向，但尚未定义管理员、成员、角色、权限或组织成员关系。过早引入未经建模的角色判断会使认证、数据归属和未来权限演进耦合。

## 决策

1. 一期中所有已登录账号拥有相同的业务操作权限，不新增管理员、成员、角色或权限表。
2. 一期授权以不可变 `accountId` 和服务端确定的当前 `tenantId` 为事实来源；任何业务读取、修改、删除和异步任务都必须验证账号/租户归属。
3. 客户端不得自行指定、伪造或提升 `accountId`、`tenantId` 或业务资源所有者。
4. RBAC 作为后续独立授权领域建设，届时先定义租户成员关系、角色、权限粒度、管理入口、审计和迁移方案，再改变接口授权规则。

## 备选方案

### 立即加入管理员与普通用户两个硬编码角色

拒绝。缺少资源、动作、组织成员关系和管理流程定义，硬编码会成为后续演进的兼容负担。

### 只验证是否已登录，不校验资源归属

拒绝。会使任意登录用户通过猜测资源标识访问或修改其他账号/租户的数据。

### 由前端控制菜单和按钮实现权限

拒绝。前端可被绕过，无法构成服务端授权边界。

## 后果

- 认证上下文必须从 Sa-Token 身份可靠解析 `accountId` 与 `tenantId`，替换当前固定用户过滤器。
- 现有 Controller、Service、Mapper 查询和异步消息处理需要审查并补齐账号/租户范围，不能只依赖 UI 隔离。
- 未来 RBAC 应在独立 ADR 中定义，且不得改变 `accountId` 对个人业务数据的基本所有权语义。
