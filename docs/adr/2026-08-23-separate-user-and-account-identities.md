# ADR：分离用户与登录账号标识

## 状态

已被《合并用户与账号持久化主体》替代。

## 背景

现有聊天等业务数据以 `user_id` 标识所有者；新认证模块还需要独立管理账号名、邮箱、密码、第三方身份、会话和角色。账号名可变且可立即释放，不能被用作稳定数据所有者。

## 决策

1. `userId` 是不可变的业务用户标识，继续用于业务数据的所有权和范围校验。
2. `accountId` 是不可变的登录账号主体标识，关联账号名、状态、邮箱、密码、第三方身份、会话与角色。
3. 一期 `userId` 与 `accountId` 严格一对一；认证上下文应同时提供二者，禁止客户端指定或替换。
4. `accountName` 是独立、可变的登录标识；改名不改变 `userId`、`accountId` 或既有业务资源归属。
5. 原固定用户 `864019719617777664` 是既有业务 `userId`，将映射到受控默认管理员账号对应的 `accountId`。

## 备选方案

### 仅保留一个 ID

拒绝。会把业务归属、登录凭据与权限主体混为一谈，使改名、数据迁移和未来多账号演进存在歧义。

### 用账号名作为业务数据外键

拒绝。账号名可更换且旧名称立即释放，无法作为稳定关联键。

### 一期支持一个用户多个登录账号

拒绝。当前需求只要求一个账号绑定多个登录凭据；引入多账号归属会额外带来账号切换、权限继承和审计歧义。

## 后果

- 认证成功后，服务端从账号关系解析可信 `userId` 与 `accountId`，再建立 Sa-Token 会话与权限上下文。
- 现有以 `user_id` 存储的业务表无需因认证接入而改为账号名；迁移时仅建立受控默认管理员账号与既有 `userId` 的映射。
- 未来若支持一个用户多个账号，必须新增独立关系模型、会话选择语义和迁移 ADR，不能放宽本期一对一约束。
