# ADR：首次第三方登录补全账号名后自动创建并登录

## 状态

已接受。

## 背景

NexaRAG 将支持 QQ、飞书、Google 和 GitHub 的扫码或 OAuth 登录，并允许一个账号绑定多个第三方身份。系统当前没有真实账号或第三方身份数据模型，只有用于开发的固定用户身份。

对于已完成第三方认证、但尚未绑定 NexaRAG 账号的外部主体，需要明确账号创建方式，避免随机账号、第三方昵称或未校验客户端输入成为业务账号标识。

## 决策

1. 未绑定的第三方身份完成服务端认证后，系统必须要求用户输入账号名。
2. 账号名必须满足既定账号规范并且未被占用；规范校验和唯一性确认均由服务端执行。
3. 校验通过后，在一个业务流程中创建账号、绑定该第三方身份、建立 Sa-Token 登录态，并为新会话签发 15 分钟最近验证授权。
4. 第三方平台返回的昵称、邮箱或用户标识不得替代用户输入的账号名。

## 备选方案

### 自动生成随机账号名并直接登录

拒绝。账号标识不可预期且难以记忆，也会把账号命名与用户意愿分离。

### 使用第三方平台昵称或邮箱作为账号名

拒绝。昵称可能为空、变化或重复；邮箱不适用于全部渠道，也不应在未确认隐私和校验规则前被强制用作公开账号标识。

### 要求用户先以既有账号登录，再绑定第三方身份

拒绝。该流程无法支持首次使用第三方登录的新用户，增加无必要的注册前置步骤。

## 后果

- 身份领域需要维护账号与第三方身份两个独立实体，并确保一个第三方身份不能同时绑定多个账号。
- 首次第三方登录接口需具备“等待补全账号名”的临时状态，且认证结果、账号名占用检查和创建操作必须防重放、防并发冲突。
- 账号名规范、账号名变更策略仍待确认；本地密码初始状态及设置/重置流程由独立 ADR 定义。
- 需要在前端明确展示补全账号名步骤，并在账号名被占用或认证会话失效时提供可恢复的提示。
