# ADR：一期引入最小管理员授权边界

## 状态

已接受。

## 背景

模型网关的裸 Chat 调用可直接消耗模型资源，提示词管理接口可改变全体运行时行为。仅用“已登录”保护这些接口，会使任意普通用户获得高风险运维能力。

## 决策

1. 一期引入以持久化 RBAC 表实现的最小角色模型：`ADMIN` 与 `USER`；角色和权限判断必须在服务端完成。
2. 模型模块的全部接口（当前为 `/api/model/**`）仅允许 `ADMIN` 访问，覆盖裸 Chat、提示词管理、路由、模型注册、供应商、模型配置和治理配置等高风险能力。
3. 原固定开发用户 `864019719617777664` 的既有业务数据将归属到受控的默认管理员账号，不得由首个普通注册账号继承。
4. `userId` 是不可变业务数据所有者，`accountId` 是不可变登录账号主体；一期两者严格一对一。账号名为独立且可变的 `accountName`。不得将现有业务表中的 `user_id` 直接、隐式改作账号名或可变登录标识。
5. 普通已登录用户保留其自身账号和租户数据范围内的既有业务能力，但无权访问上述管理员接口。
6. 一期不提供管理员对其他用户授予、转让或撤销 `ADMIN` 角色的 API、界面或普通运维入口；除默认管理员外的新账号均为 `USER`。
7. RBAC 持久化模型使用 `auth_role`、`auth_permission`、`auth_account_role` 与 `auth_role_permission` 四张表；后续以实际表结构审查权限粒度与演进方式。

## 备选方案

### 仅由前端隐藏管理员菜单

拒绝。客户端控制可以被直接绕过，不能构成授权边界。

### 继续所有登录用户拥有同一业务权限

拒绝。模型消耗和提示词发布均属于高影响操作，需要最小服务端权限分离。

### 一期直接构建完整多租户 RBAC

拒绝。组织成员、角色自定义、权限矩阵与管理流程尚未定义；本期先以固定的最小角色解决已知高风险边界。

## 后果

- Sa-Token 需要从 `accountId` 对应的 RBAC 关系可靠读取当前主体角色和权限，并在 Controller/统一鉴权层强制校验。
- 新增 `/api/model/**` 接口时必须默认继承管理员边界；普通用户仅通过受业务数据范围约束的常规业务接口间接使用模型能力。
- 角色授予、变更和默认管理员初始化均应纳入安全审计；不得由开放注册、客户端请求或账号名猜测取得管理员权限。
- 默认管理员不可用时的恢复机制属于受控部署运维流程，需独立定义；不得临时暴露角色管理接口绕过本决策。
