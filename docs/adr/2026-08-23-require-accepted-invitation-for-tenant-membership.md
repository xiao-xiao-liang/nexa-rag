# ADR：企业租户成员资格通过受邀用户确认建立

## 状态

已接受。

## 背景

企业租户可能承载私有资料。仅由租户所有者输入账号名或邮箱直接加入成员，可能因录入错误将资料暴露给非预期用户；同时被邀请者也应明确知晓其加入的组织空间。

## 决策

1. 仅具有租户内 `OWNER` 角色的成员可向现有用户发起企业租户邀请。
2. 邀请目标以已验证邮箱或账号名定位，但服务端必须解析到唯一可信 `userId`；不得信任客户端提交的 userId。
3. 受邀用户须在有效登录态中明确接受邀请，接受后才创建有效的用户—租户成员资格。
4. 邀请未接受、被拒绝、撤销、过期或目标不存在时，不得赋予目标用户该企业租户的任何访问权限。
5. 邀请、接受、拒绝、撤销与过期均需审计；对外响应应避免向未认证者泄露账号或邮箱是否存在。
6. `OWNER` 可撤销尚未接受的邀请，也可移除已加入的 `MEMBER`；多所有者和最后所有者保护在后续成员角色设计中另行定义。
7. `MEMBER` 可自行退出企业租户；退出后立即失去访问权并触发当前租户回退。唯一所有者不得自行退出，以避免产生无所有者租户。

## 备选方案

### 租户所有者直接添加成员

拒绝。账号或邮箱录入错误会立即造成企业数据越权可见，且被加入者无法知情确认。

### 允许任意已登录用户自行申请加入

拒绝。没有受控审批时会造成租户发现与成员资格滥用。

### 通过公开注册链接自动加入

拒绝。链接泄露和转发难以约束实际接受主体，且不能替代已登录身份校验。

## 后果

- 身份与租户数据模型需要保存邀请对象、目标租户、状态、有效期及审计关联；精确字段在表结构设计时审查。
- 前端需提供受邀用户查看并接受/拒绝其待处理邀请的入口；服务端必须再次验证当前用户与邀请目标一致。
- 成员移除会触发当前租户失效回退规则；需要在后续设计中定义多租户成员角色、退出和多所有者治理。
- 退出与移除均不得删除用户账号、全局角色、其他租户成员资格或历史审计记录。
