# ADR：知识库首期固定单租户，并预留认证上下文接口

## 状态

已接受。

## 背景

知识库已确定按租户隔离，但当前认证模块仅通过固定过滤器提供 `userId`，不具备真实登录、租户解析或组织成员鉴权能力。立即引入完整多租户认证会扩大本期知识库改造范围；忽略租户字段又会让后续接入 Sa-Token 时产生数据迁移和接口兼容风险。

## 决策

1. 首期以一个内建默认租户运行，当前请求的租户由服务端上下文确定，不接受客户端直接指定的租户标识。
2. 新增知识库及其关联数据从首期开始保存租户归属字段，并在服务层按“当前租户”封装查询与写入边界。
3. 定义独立的当前租户提供者抽象；首期实现返回内建默认租户，后续由 Sa-Token `auth` 模块的登录身份和组织关系实现替换。
4. Sa-Token 登录鉴权、租户选择、组织成员关系、角色与权限策略不进入本期知识库改造范围。

## 备选方案

### 本期直接接入 Sa-Token 多租户鉴权

暂不采用。认证、组织和授权是独立的跨模块项目，会放大当前知识库数据模型与接口改造的交付风险。

### 本期完全不持久化租户字段

拒绝。后续接入真实租户时无法可靠回填历史数据，也容易遗漏跨租户检索和查询过滤。

### 由每个业务请求传入 `tenantId`

拒绝。客户端参数不能作为隔离事实，未来也会与登录态中的租户归属冲突。

## 后果

- 需要确定稳定的内建默认租户标识，并通过迁移初始化。
- 存量数据迁移、索引元数据与所有知识库查询均要使用该默认租户，后续认证接入时只替换当前租户来源。
- 首期仅能验证单租户下多知识库的分组与检索隔离，不能声称已具备真实组织间访问控制。
