# ADR：无邮箱账号绑定首个已验证邮箱

## 状态

已接受。

## 背景

通过 QQ、飞书、Google 或 GitHub 首次登录创建的账号初始不强制拥有 NexaRAG 已验证邮箱，但用户仍应能启用邮箱验证码登录、邮箱密码登录和密码找回。该账号不存在旧邮箱，不能套用更换邮箱的双邮箱验证流程；仅凭三天登录态直接增加恢复与登录凭据又会放大会话被盗风险。

## 决策

1. 对当前没有已验证邮箱的已登录账号，提供“绑定邮箱”安全设置操作。
2. 绑定首个邮箱必须同时满足：当前 Sa-Token 会话拥有未过期的最近验证授权，且目标新邮箱已完成绑定邮箱用途的一次性验证码验证。
3. 绑定验证码与邮箱登录、注册、密码设置/重置及邮箱更换用途隔离、短期有效且单次消费；最近验证授权只能证明当前账号控制权，不能替代新邮箱的归属证明。
4. 目标邮箱必须通过全局唯一归属检查；账号、已验证邮箱归属和验证码消费应原子写入。成功后，该邮箱立即成为该账号唯一可用的邮箱验证码登录、邮箱密码登录、设置密码和密码重置凭据。
5. 首个邮箱绑定成功不撤销该账号既有 Sa-Token 会话，也不自动延长或重新签发最近验证授权。

## 备选方案

### 第三方首次登录时强制填写邮箱

拒绝。会在最小化第三方注册流程中增加不必要的前置步骤，且用户可稍后自行选择是否启用邮箱登录和恢复渠道。

### 仅验证新邮箱，不要求最近验证授权

拒绝。只能证明操作者控制目标邮箱，不能证明其有权为当前 NexaRAG 账号新增登录与恢复入口。

### 把首个邮箱绑定视作双邮箱更换

拒绝。账号尚无旧邮箱，无法完成旧邮箱证明；应使用当前会话最近验证授权补足当前账号控制权证明。

## 后果

- 账号的已验证邮箱字段或独立邮箱凭据记录必须允许为空，以支持仅第三方登录的账号。
- 安全设置前端应在无已验证邮箱时展示“绑定邮箱”，有已验证邮箱时展示“更换邮箱”；两条流程不得混用验证码用途。
- 绑定过程必须写入安全审计日志，记录 `accountId`、结果和时间，不得记录验证码、会话 Token 或完整 Cookie。
