# ADR：创建企业租户时建立初始所有者成员资格

## 状态

已接受。

## 背景

共享默认租户继续承载公开注册账号的默认业务范围。管理员可创建新的企业租户；仅有租户主数据无法回答谁可访问该租户，因此必须同时建立成员资格。

## 决策

1. 租户以独立的持久化租户主数据表保存，不以配置字符串或业务表字段替代。
2. 管理员创建企业租户时，创建者自动成为该租户唯一初始成员与所有者。
3. 用户与租户的成员资格使用独立关系表达，语义上关联不可变 `userId` 与 `tenantId`；不得把全局 `ADMIN` / `USER` 角色表当作租户成员关系。
4. 新企业租户创建后，除初始所有者外，其他用户仅能在接受有效邀请并建立成员资格后访问其数据。
5. 企业租户创建、初始成员建立和失败回滚必须原子完成并写入审计。
6. 租户成员关系一期仅使用 `OWNER` 与 `MEMBER` 两种租户内角色：`OWNER` 可治理成员，`MEMBER` 可使用该租户业务数据；两者均不因此获得全局 `ADMIN` 权限。
7. `OWNER` 可将该企业租户的所有者身份转交给现有成员；发起转交前必须完成最近验证。该操作只影响租户内角色，不得改变全局 `ADMIN` / `USER` 角色。
8. 所有者转交采用双确认：接收成员在登录状态下明确接受后才生效；生效后原所有者降为 `MEMBER`，租户始终保留有效 `OWNER`。

## 备选方案

### 只有租户表，不保存成员

拒绝。无法形成服务端可验证的访问范围，任何租户访问都将依赖不可信客户端参数或隐式规则。

### 让所有默认租户用户自动加入新企业租户

拒绝。新企业空间可能包含私有资料，自动加入会造成越权访问。

### 以全局管理员角色代替租户所有者

拒绝。全局模型管理权限与某个企业空间的成员资格是不同授权维度，不能混用。

## 后果

- 租户数据模型至少需要租户主数据与用户—租户成员关系；成员关系的字段、邀请和切换规则将在后续设计中确定。
- 资源读写必须同时校验当前可信用户是否拥有目标租户的有效成员资格。
- 后续可扩展租户级角色与成员状态，但不应改变初始所有者自动建立的语义或混用全局角色。
- 多所有者规则需在后续成员角色设计中明确；一期转交不得产生无所有者状态。
