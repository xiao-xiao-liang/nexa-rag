# ADR：API 默认拒绝并按认证与权限放行

## 状态

已接受。

## 背景

当前系统从固定开发用户过渡到真实账号。若仅依赖各业务 Controller 自行决定是否校验登录，新增接口容易遗漏认证；若把整个认证路径无差别匿名放行，又会扩大敏感账号操作的攻击面。

## 决策

1. `/api/**` 默认要求有效 Sa-Token 登录态；不因前端路由、请求来源或客户端携带的用户标识而绕过。
2. 仅完成登录、注册、邮箱验证码挑战、密码重置、OAuth 发起/回调及默认管理员首次激活所必需的具体认证动作可匿名访问。
3. 已登录的账号设置、绑定解绑、邮箱更换、设备管理、安全活动及所有业务数据接口均要求当前登录态，并按其各自规则执行最近验证、数据归属和角色检查。
4. `/api/model/**` 在有效登录态基础上额外要求 `ADMIN` 对应权限；普通用户不得访问。
5. 新增 API 必须显式归类为匿名认证动作、已登录业务动作或特权动作；未归类时沿用默认拒绝。

## 备选方案

### Controller 自行决定是否校验登录

拒绝。易被遗漏且难以集中审计，无法形成统一安全边界。

### 整个 `/api/auth/**` 匿名放行

拒绝。认证路径也包含已登录后的敏感设置，按路径整体放行会绕过会话与二次验证要求。

### 仅区分已登录和未登录

拒绝。模型管理需要额外的管理员权限边界。

## 后果

- Sa-Token 配置和测试需要覆盖默认拒绝、匿名入口白名单、普通已登录接口与管理员接口四种情形。
- API 设计文档必须逐项标明访问前置条件；认证相关接口也不得因路径名称被默认信任。
- 未登录访问应返回统一的未认证语义，已登录但无权访问应返回明确的未授权语义，避免混淆客户端处理逻辑。
