# ADR：会话打开时仅加载最近二十条消息

## 背景

用户在前端切换会话时需要等待历史消息接口返回。一次传输过多消息会增加数据库读取、序列化、网络传输和 Markdown 渲染成本，并造成可感知的加载态。现有历史接口已经按 `sequence` 提供游标分页能力，消息原文仍由 MySQL 完整保存。

## 决策

打开已有会话时，前端仅请求并立即展示最新 20 条历史消息。若接口返回 `hasMore=true`，用户上滑至消息列表顶部时，前端使用当前最早已展示消息的 `sequence` 作为 `beforeSequence` 请求更早的一页，并将结果追加到列表顶部且保持滚动位置。

数据库完整历史仍是唯一事实源；该决定只约束首屏展示投影和单页读取大小，不删除、不截断历史消息，也不将 Redis 作为历史主存储。

## 备选方案

1. 打开会话时读取 50 条消息。
2. 打开会话时读取完整历史。
3. 保持 50 条首屏读取，仅依赖 Redis 缓存降低延迟。

## 理由

20 条通常足以恢复用户刚刚离开的对话上下文，同时显著降低首次响应的消息负载。游标分页避免深 Offset 带来的扫描成本，且可渐进加载完整历史。该方案优先改善用户可见延迟，不要求新增基础设施或改变现有数据事实来源。

## 后果

- 历史接口默认 `size`、前端首次调用参数和相关测试应统一为 20。
- 前端需要实现顶部触发、请求去重、错误提示、结果去重和加载前后的滚动锚点保持。
- 已访问会话可使用前端内存历史页缓存后立即渲染，并在后台刷新；缓存失效后仍以接口结果为准。
- 历史记录数量很大时，旧消息仍按页读取，不会因首屏策略导致传输全量历史。
